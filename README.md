# Northstar Homes – AI Sales Bot

A simple full-stack AI conversational sales assistant for a fictional real-estate company, Northstar Homes. The bot plays the role of **Riya**, a warm and consultative sales consultant for the **Northstar One** project in Sector 79, Gurugram.

Built as a take-home assignment. Designed for correctness and clarity over cleverness.

---

## Tech Stack

| Layer    | Technology                                              |
|----------|---------------------------------------------------------|
| Backend  | Node.js + Express                                       |
| LLM      | Groq API (`llama-3.3-70b-versatile`)                    |
| Frontend | Single static HTML page, vanilla JS, no build step      |
| Storage  | In-memory (no database)                                 |

## How to Run Locally

### Prerequisites

- **Node.js 18+** (native `fetch` is required — no `node-fetch` dependency needed)
- A **Groq API key** — get one free at [console.groq.com](https://console.groq.com)

### Steps

```bash
# 1. Install dependencies
npm install

# 2. Create your .env file from the template
copy .env.example .env
# Then open .env and replace 'your_key_here' with your actual GROQ_API_KEY

# 3. Start the server
npm start

# 4. Open your browser
# Navigate to http://localhost:3000
```

## Key Assumptions

1. **Date-parsing heuristic for booking failure detection**: The server uses a lightweight regex-based approach to detect common date formats in user messages (DD/MM/YYYY, DD-MM-YYYY, YYYY-MM-DD, "15 August", "August 15", "yesterday"). If a detected date is before today, an ephemeral system note is injected into the LLM context for that turn only. This does not catch every possible date expression (e.g., "last Friday") — the LLM's own guardrail instructions cover ambiguous cases.

2. **In-memory session storage**: Conversation histories are stored in a plain JavaScript object keyed by `sessionId`. Sessions are not persisted across server restarts. This is intentional given the scope of the assignment.

3. **Single project knowledge base**: Riya knows facts about exactly one project — Northstar One. The system prompt is the single source of truth; no external database or CMS is involved.

4. **No real voice integration**: The system prompt is written to be voice-compatible in tone and output format (plain sentences, no markdown), but this prototype only implements text chat.

5. **Session cleanup on end**: Calling `POST /api/end-session` deletes the session from memory after generating analytics. Refreshing the page generates a new `sessionId`, starting a fresh session.

---

## Known Limitations

- **Date parsing is imperfect**: Relative expressions like "last Friday", "a week ago", or "3 days back" are not caught by the heuristic. The LLM prompt includes a booking-failure guardrail to compensate, but the ephemeral system note won't be injected for these cases.
- **No persistent storage**: All conversation data is lost on server restart. A production system would use a database (e.g., PostgreSQL or Redis).
- **No authentication**: Session IDs are UUIDs generated client-side. In production, these would be tied to authenticated user accounts.
- **Single-server, single-process**: Sessions live in one Node.js process. A multi-process/cluster setup would require a shared store (e.g., Redis).
- **No real voice channel**: Despite the voice-compatible prompt, there is no telephony or WebSocket integration. Text-only.
- **Analytics accuracy depends on LLM**: The `end-session` analytics are generated by an LLM, not deterministic rules, so edge cases may produce imperfect JSON or classification.
